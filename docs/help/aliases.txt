Aliases page

This page creates and manages additional hostnames that point at an existing mapped service without changing the original route.

How to use it:
- Choose a mapped domain from the list to use as the source host.
- Choose a suggested project name from the Alias combobox, or type your own hostname such as hello.local.dev-gutools.co.uk.
- Suggestions come from the selected container's Dev Container name metadata or project folder, including VS Code and IntelliJ labels. They do not change the original route.
- Click Add alias to create the secondary hostname and reload the page.
- Use Delete to remove a manual alias. Automatic aliases come from a Dev Container's metadata name when it has one route and no hostname collision.
- Primary routes and manual aliases take precedence. If multiple containers claim the same automatic alias, none gets it.

Requirements:
- The source hostname must already be mapped and active in the current chekov configuration.
- When using POST /api/aliases, sourceHostname and alias may omit the configured base domain. For example, sourceHostname=api and alias=api-public use api.local.dev-gutools.co.uk and api-public.local.dev-gutools.co.uk with the default base domain.
- To alias Chekov's own UI, use POST /api/aliases with sourceHostname=chekov. The alias survives route refreshes, although Chekov's UI is not listed in the source dropdown.
- The alias must be a valid hostname and must not already be in use.
- The generated nginx config must reload successfully before the alias becomes available.

Aliases are useful when one service needs a friendly or temporary hostname while still sharing the same underlying route and backend.
